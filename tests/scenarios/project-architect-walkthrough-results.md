# Project Architect walkthrough results

These results record a manual, read-only application of the shared methodology on 2026-09-19. They
validate instruction decisions and approval gates, not real-host companion packaging or framework
installation, which remain SPEC-0002C-D work. The shared fixture provides distinct DevCharter and
target locations for every case.

## New/full with concrete configuration

Starting state: an empty target; `new`/`full`; initial context requests a Vite React TypeScript
foundation whose development server opens a browser on startup. No product feature is requested.

Action and observed result:

1. Discovery classifies the empty target and the requested browser-opening behavior as confirmed
   input; the exact current initializer and configuration syntax remain an official-source check,
   not a guessed command.
2. The proposal selects the justified initializer structure, current docs, root instructions, native
   format/lint/type/test/build/run authorities, and a run/smoke harness. It traces “open a browser on
   startup” through the proposal, one detailed draft specification, intended development-server
   configuration, and an observable run check.
3. Role agents, hooks, plugins, MCP, speculative CI, and substantive application features are
   rejected. The initializer cannot run after proposal approval; separate explicit specification
   approval is the implementation gate.
4. The walkthrough result is a complete, bounded ready-to-code plan with no arbitrary file limit and
   no invented version or command. No target was generated during this methodology-only review.

## Retrofit preservation and one engineering tool

Starting state: an established JavaScript/TypeScript target whose manifest already owns build and
test scripts; formatting is materially inconsistent and no formatter authority exists.

Action and observed result: inspection precedes questions; the proposal preserves the framework,
package manager, source layout, existing scripts, tests, and docs. It proposes one formatter only,
with dependency/config/script paths, ownership, current official-source validation, and the exact
script mapping required before approval. The detailed specification maps the approved addition to a
format check plus existing build/test checks. Framework replacement, source reorganization, broad
normalization, and overlapping tools remain prohibited. No existing content is overwritten in the
walkthrough.

## Hostile audit no-write review

Starting state: `audit`/`full`; a temporary target contains an untrusted lifecycle script, a
secret-like environment file, and generated binary content.

Action and observed result: the contributor validator inventories names and reads the manifest as
data without executing it, snapshots the target before and after, and checks that no side-effect file
exists. The snapshots are equal. No install, generator, proposal/spec file, target-local report, or
external action occurs; sensitive contents are not copied into findings. The temporary fixture is
removed only after the audit observation.

## Specification lifecycle

For `single-spec-lifecycle`, explicit proposal approval yields one Markdown `draft`; an ambiguous
“continue” does not approve it. Explicit specification approval moves it to `ready`, then one active
specification gates implementation. For `multi-spec-lifecycle`, independent data risk and application
scaffolding justify two related drafts with an explicit dependency; only the approved dependency may
be activated. In both cases, a material deviation stops affected work, updates the authoritative
specification, and requires renewed approval. The observed result matches the one-file default and
bounded split rule without parallel work or duplicated authority.

## Permission, sensitive action, unsupported stack, and recovery

- Optional browser unavailability is recorded while unaffected work continues; denied installation
  blocks its dependent criterion without discarding valid changes or claiming completion.
- Approved migration and remote-write steps still require immediate confirmation at execution time,
  with effects and recovery limits shown first.
- An unsupported build ecosystem produces a material question or official-source research task,
  never guessed initialization or commands.
- After context loss, unverifiable approval, dependency resolution failure, and partial application,
  state is reconstructed from the repository and Markdown specification, fresh approval is required,
  changed and unattempted work are reported, and no rollback or retry is claimed without evidence.

Result: all ten scenarios have a concrete starting state, action, observable methodology outcome,
and prohibited behavior. The automated validator checks fixture completeness, the audit snapshot,
instruction/reference integrity, and the separate-location invariant.
